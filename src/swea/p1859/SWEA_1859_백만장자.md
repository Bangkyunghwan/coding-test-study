# SWEA 1859 — 백만 장자 프로젝트

**알고리즘:** 그리디(Greedy), 역방향 탐색, 최댓값 갱신  
**시간 복잡도:** O(N²) → O(N)  
**핵심:** 중복 계산을 제거하기 위해 탐색 방향을 바꾼다.

## 1. 처음 접근 방식과 문제점

각 날짜를 기준으로 이후 날짜들의 가격을 모두 비교해서 가장 높은 가격을 찾고, 그 차익을 합산하려고 했다.

- 알고리즘의 논리 자체는 맞았다.
- 하지만 매 날짜마다 이후 날짜의 최댓값을 새롭게 계산했다.
- 이미 탐색했던 원소를 계속 다시 탐색하는 중복 계산이 발생했다.
- 이중 반복문으로 인해 시간 복잡도가 O(N²)이 되어 시간 초과가 발생했다.

**문제점은 최댓값을 구하는 것이 아니라, 최댓값을 매번 처음부터 다시 구했다는 것이다.**

## 2. 어떻게 생각했어야 했을까?

### ① 중복 계산을 발견한다

각 날짜에서 필요한 정보는 **현재 날짜 이후의 최댓값**이다.

그런데 다음 날짜에서도 거의 동일한 구간의 최댓값을 구하고 있었다.

→ 이전에 계산한 최댓값을 재활용할 수 없을까?

### ② 탐색 방향을 고민한다

왼쪽부터 탐색하면 현재 날짜 이후의 최댓값을 아직 알 수 없다.

반대로 오른쪽부터 탐색하면 이미 확인한 날짜들이 모두 현재 날짜 이후에 해당한다.

→ 오른쪽부터 탐색하면서 최댓값을 기억하면 된다.

### ③ 이전 계산 결과를 재활용한다

현재 날짜부터 마지막 날짜까지의 최댓값은 다음 두 값 중 큰 값이다.

- 현재 날짜의 가격
- 다음 날짜부터 마지막 날짜까지의 최댓값

즉, `max(i) = max(prices[i], max(i + 1))`이다.

따라서 오른쪽부터 순회하면서 최댓값 하나만 유지하고 갱신하면 된다.

```java
int max = prices[N - 1];
long profit = 0;

for (int i = N - 2; i >= 0; i--) {
    if (prices[i] > max) {
        max = prices[i];
    }

    profit += max - prices[i];
}
```

각 원소를 한 번씩만 확인하기 때문에 O(N)에 해결할 수 있다.

## 3. 이번 문제에서 배운 점

**① 중복 계산을 찾아야 한다.**

이중 반복문을 작성했다면 같은 원소나 같은 구간을 여러 번 탐색하고 있는지 확인한다. 다만 이중 반복문 자체가 무조건 잘못된 것은 아니다.

**② 이전에 계산한 결과를 재활용할 수 있는지 생각한다.**

최댓값이나 최솟값처럼 이전 계산 결과를 갱신하는 것만으로 답을 구할 수 있는 경우가 있다.

**③ 탐색 방향을 바꿔본다.**

현재 위치 이후의 정보가 필요하다면 오른쪽부터 탐색하는 것이 유리할 수 있다.

**④ 시간 복잡도를 고려한다.**

입력 크기가 클 때는 O(N²)이 시간 초과를 일으킬 수 있다. 정답을 구하는 방법을 찾은 후에는 연산량도 확인해야 한다.

**⑤ 자료형의 범위를 확인한다.**

개별 입력값은 `int` 범위여도 누적합은 `int` 범위를 초과할 수 있다. 이번 문제에서는 최종 이익을 `long`으로 저장해야 한다. 모든 숫자에 무조건 `long`을 쓸 필요는 없다.

## 4. 앞으로 문제를 풀 때 생각할 순서

1. 우선 정답을 구할 수 있는 가장 직관적인 알고리즘을 생각한다.
2. 입력 범위와 시간 복잡도를 확인한다.
3. 시간 초과가 예상된다면 어떤 계산을 반복하고 있는지 확인한다.
4. 이전 계산 결과를 재활용할 수 있는지 고민한다.
5. 탐색 방향이나 자료구조를 바꾸면 중복 계산을 제거할 수 있는지 생각한다.

## 5. 최종 핵심 정리

이번 문제는 단순히 반복문을 줄이는 문제가 아니었다.

**각 날짜 이후의 최댓값을 매번 계산하던 방식에서, 역방향으로 탐색하며 이전에 구한 최댓값을 재활용하는 방식으로 사고를 전환하는 것이 핵심이었다.**

앞으로 기억할 질문:

> 내가 지금 계산하는 값은 이전에 계산한 결과를 이용해서 더 쉽게 구할 수 없을까?

> 탐색 순서를 바꾸면 필요한 정보를 미리 알고 있는 상태에서 계산할 수 있지 않을까?
