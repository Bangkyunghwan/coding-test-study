# 프로그래머스 42576 — 완주하지 못한 선수

**문제 유형:** 문자열, 정렬 (다른 풀이: 해시맵)  
**시간 복잡도:** 처음 접근 O(N²) → 최종 풀이 O(N log N)  
**핵심:** 두 배열이 단 한 명을 제외하고 같은 원소들로 이루어져 있다는 조건을 이용한다.

## 1. 문제 이해

- `participant`: 마라톤에 참가한 선수들의 이름 배열
- `completion`: 완주한 선수들의 이름 배열
- 참가자 중 **단 한 명만 완주하지 못했다.**
- **동명이인이 존재할 수 있다.** 따라서 이름이 있는지만 확인해서는 안 되고, 같은 이름이 몇 번 등장했는지도 고려해야 한다.

## 2. 처음 접근 방식과 문제점

처음에는 문제 자체가 단순해서 **참가자와 완주자를 모두 비교하는 방법**을 생각했다.

1. 참가자 한 명을 선택한다.
2. `completion` 배열을 전부 돌면서 이름이 같은 사람을 찾는다.
3. 찾았다면 이미 매칭된 완주자를 다시 사용하지 않도록 `""`로 바꾼다.
4. 완주자와 매칭되지 않는 참가자를 반환한다.

동명이인이 있을 수 있으므로, 한 번 매칭한 완주자를 제거하는 방식으로 처리하려고 했다.

```java
class Solution {
    public String solution(String[] participant, String[] completion) {
        for (String participantPerson : participant) {
            int count = 0;
            for (int i = 0; i < completion.length; i++) {
                if (participantPerson.equals(completion[i])) {
                    count++;
                    completion[i] = "";
                }
            }

            if (count == 0) {
                return participantPerson;
            }
        }
        return "";
    }
}
```

### 문제점 ① 동명이인 처리 오류

`completion`에도 같은 이름이 여러 번 등장하면 **참가자 한 명이 여러 명의 완주자와 매칭**될 수 있다.

```text
participant = ["a", "a", "b"]
completion  = ["a", "a"]
정답 = "b"
```

첫 번째 `"a"`를 검사할 때 완주자 `"a"` 두 명을 모두 `""`로 바꾸기 때문에, 두 번째 참가자 `"a"`가 미완주자로 잘못 판단된다.

→ **하나를 매칭했다면 `break`로 내부 반복문을 종료해야 한다.** 그러면 논리적으로는 답을 구할 수 있다.

### 문제점 ② 시간 복잡도 O(N²)

참가자마다 완주자 배열을 다시 순회하므로 최악의 경우 O(N²)이다.

참가자가 최대 100,000명이므로 비교가 약 100억 번까지 늘어날 수 있다. 논리 오류를 고치더라도 이 방법은 시간 초과 가능성이 크다.

**완전탐색을 먼저 떠올린 것 자체는 괜찮지만, 구현 전에 입력 크기와 시간 복잡도를 확인해야 한다.**

## 3. 정렬을 이용한 접근으로 개선

처음에는 모든 이름을 비교하는 것 말고는 방법이 떠오르지 않았다. `Set`도 생각했지만, 중복되는 이름을 구분할 수 없어 적절하지 않다고 판단했다.

그러다가 **두 배열이 한 사람만 제외하고 거의 동일한 원소들로 구성되어 있다는 점**에 주목했다.

> 그렇다면 두 배열을 먼저 정렬하면, 같은 인덱스의 이름끼리 비교할 수 있지 않을까?

정렬하면 같은 이름들이 모이고 양쪽 배열의 순서가 맞춰진다.

```text
participant (정렬): ["ana", "bob", "kim", "lee"]
completion  (정렬): ["ana", "bob", "lee"]
                             ↑
                     처음으로 달라지는 위치
```

- 같은 인덱스에서 **처음으로 이름이 달라지면** 그 위치의 `participant`가 미완주자이다.
- `completion`의 마지막까지 전부 같다면 **`participant`의 마지막 원소**가 미완주자이다.
- 동명이인이 있어도 두 배열을 정렬하면 같은 이름이 연속으로 놓이므로 이 방식이 성립한다.

### 최종 제출 코드

```java
import java.util.*;

class Solution {
    public String solution(String[] participant, String[] completion) {
        Arrays.sort(participant);
        Arrays.sort(completion);

        for (int i = 0; i < completion.length; i++) {
            if (!completion[i].equals(participant[i]))
                return participant[i];
        }

        return participant[participant.length - 1];
    }
}
```

### 시간 복잡도

- `participant` 정렬: O(N log N)
- `completion` 정렬: O(N log N)
- 같은 인덱스끼리 비교: O(N)

따라서 전체 시간 복잡도는 **O(N log N)**이다. (문자열 자체의 비교 비용은 문자열 길이에 따라 추가될 수 있다.)

정렬을 통해 이중 반복문을 없애고, 한 번의 순회로 답을 찾을 수 있게 되었다.

## 4. 구현하면서 겪은 실수와 배운 문법

### ① 문자열 비교는 `equals()`

정렬 방식 자체는 이미 생각해서 구현해 봤지만, 처음에는 문자열을 `!=`로 비교해서 실패했다.

```java
// 잘못된 비교: 문자열 내용이 아니라 참조를 비교
if (completion[i] != participant[i]) { ... }

// 올바른 비교: 문자열 내용 비교
if (!completion[i].equals(participant[i])) { ... }
```

`==`, `!=`는 객체의 참조가 같은지 비교한다. **문자열의 내용이 같은지 판단할 때는 `equals()`를 사용한다.** (`equal()`이 아니라 `equals()`.)

### ② 배열 정렬: `Arrays.sort()`

```java
Arrays.sort(participant);
Arrays.sort(completion);
```

- 배열 자체를 오름차순으로 정렬한다. **원본 배열이 변경된다.**
- `String[]`는 기본적으로 문자열의 자연 순서(사전순에 가까운 문자 순서)로 정렬된다.
- 객체 배열 정렬에는 TimSort가 사용되며 O(N log N)으로 분석할 수 있다.

### ③ 배열 출력 확인: `Arrays.toString()`

```java
System.out.println(Arrays.toString(participant));
```

배열 전체의 원소를 확인할 때 사용한다.

### ④ 리스트와 배열의 정렬 방법 구분

```java
Arrays.sort(arr);          // 배열
Collections.sort(list);    // ArrayList 등 리스트
```

### ⑤ `Set`과 `Map`의 차이

- `Set`: 같은 원소를 중복 저장하지 않으므로 이름별 인원수를 보존하지 못한다.
- `HashMap<String, Integer>`: 이름별 등장 횟수를 저장할 수 있으므로 동명이인도 처리할 수 있다.
- 해시맵을 이용하면 평균 O(N)으로도 해결할 수 있지만, **이번에 직접 구현한 최종 풀이는 정렬 방식**이다.

## 5. 시간 제한이 명시되지 않았을 때의 판단

프로그래머스처럼 시간 제한이 따로 보이지 않아도 **최대 입력 크기를 기준으로 시간 복잡도를 먼저 계산**한다.

이번 문제에서 N = 100,000이라고 하면:

| 시간 복잡도 | 대략적인 연산 횟수 |
| --- | ---: |
| O(N) | 10만 |
| O(N log₂ N) | 약 166만 |
| O(N²) | 100억 |

정확한 실행 시간은 연산의 종류와 실행 환경에 따라 다르지만, N이 10만일 때 O(N²)은 위험하다고 판단할 수 있다.

일반적으로 증가 속도는 **O(N) < O(N log N) < O(N²)** 이다. 다만 실제 실행 시간이 항상 이 순서로 정해지는 것은 아니다.

## 6. 앞으로 비슷한 문제를 볼 때 생각할 순서

1. **가장 직관적인 방법을 생각한다.** 전체를 비교하면 풀리는가?
2. **입력 범위를 확인한다.** 이중 반복문을 사용해도 되는 크기인가?
3. **문제에서 주어진 관계를 찾는다.** 두 배열이나 집합이 거의 같거나, 일부 원소만 다른가?
4. **정렬하면 비교가 쉬워지는지 생각한다.** 정렬 후 같은 인덱스끼리 비교하거나 순서대로 탐색할 수 있는가?
5. **중복 원소를 고려한다.** 존재 여부만 확인하면 되는가, 등장 횟수도 필요한가?
6. **예외 상황과 문법을 확인한다.** 마지막 원소가 답인 경우, `equals()` 사용 등을 놓치지 않았는가?

## 7. 최종 핵심 정리

이번 문제에서는 **참가자마다 완주자 전체를 검색하던 O(N²) 방식**에서 시작했다.

완전탐색에도 동명이인 매칭 오류가 있었고, 이를 고쳐도 입력 크기 때문에 비효율적이었다. 이후 **두 배열이 딱 한 사람만 다르다**는 성질을 이용해 정렬을 떠올렸고, 정렬 후 같은 인덱스끼리 비교하는 O(N log N) 풀이로 개선했다.

처음 정렬 풀이가 실패했던 이유도 알고리즘이 아니라 **문자열을 `!=`로 비교한 문법 실수**였다.

> **정렬하면 원소들에 순서가 생긴다. 이 순서를 이용해 원래 모든 원소를 비교해야 했던 작업을 줄일 수 없는지 생각해 보자.**
